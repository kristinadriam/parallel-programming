# ДЗ-6: memory reordering

## постановка

в программе есть общие для потоков поле `data` и флаг готовности `ready`. поток-писатель выставляет данные и взводит флаг. поток-читатель крутится на флаге и по факту готовности читает данные:

```text
писатель:  data = i;        ready = i;
читатель:  r = ready;   if (r новое)   d = data;
```

в программном порядке `data` всегда получает значение `i` раньше, чем `ready`. значит на корректно упорядоченной машине читатель, увидевший `ready == r`, обязан прочитать `data >= r`. если же он наблюдает `data < r`, произошло переупорядочивание: либо у писателя переставились две записи (StoreStore), либо у читателя — два чтения (LoadLoad). именно событие `data < ready` и считаем аномалией.

тип флага переключается на этапе компиляции:

* `-DFLAG_PLAIN` — обычный `volatile int` (гонка данных, UB).
* `-DFLAG_ATOMIC_RELAXED` — `std::atomic<int>` с `memory_order_relaxed`.
* `-DFLAG_ATOMIC_ACQREL` — `std::atomic<int>` с `release`/`acquire` (корректный вариант).

число итераций: $2\times 10^8$ для нативных запусков, $10^7$ для QEMU.

| режим флага | x86-64 нативно (VM) | aarch64 под QEMU (VM) | arm64 нативно (M1) |
| --- | --- | --- | --- |
| `volatile int` (plain) | 0 | 0 | 1 509 945 |

| `atomic`, `release/acquire` | 0 | 0 | 0 |

## эксперимент на x86

на нативном x86-64 аномалий нет ни в одном режиме. причина — модель памяти x86 Total Store Order: она запрещает переупорядочивание StoreStore и LoadLoad. поэтому если читатель увидел `ready == r`, то запись `data = r`, выполненная писателем раньше, гарантированно уже видна — всегда `data >= r`.

это подтверждается сгенерированным кодом: на x86 запись флага в режимах `relaxed` и `release` транслируется в одну и ту же инструкцию:

```asm
; x86-64, и relaxed, и release — идентично:
    movl   $1, data(%rip)
    movl   $1, ready(%rip)     ; обычный store, mfence отсутствует
    ret
```

## эксперимент на ARM

на нативном arm64 (M1) аномалии массовые: ~1.5 млн для `volatile` и ~1.9 млн для `relaxed`. причина — weak модель памяти ARM: она допускает и StoreStore-, и LoadLoad-переупорядочивание. запись во флаг может стать видимой другому ядру раньше записи в данные, а чтения у читателя могут выполниться не в программном порядке. в результате читатель периодически видит новый `ready` при еще старом `data` (`data < ready`).

сгенерированный код объясняет, почему так и почему `release/acquire` это лечит:

```asm
; ARM, запись флага:
relaxed:   str   w2, [x0]      ; обычная запись -> StoreStore разрешен
release:   stlr  w2, [x0]      ; Store-Release -> data гарантированно записан раньше

; ARM, чтение флага:
relaxed:   ldr   w2, [x0]      ; обычная загрузка -> LoadLoad разрешен
acquire:   ldar  w2, [x0]      ; Load-Acquire -> последующее чтение data не уедет вперед
```

барьерные инструкции `stlr`/`ldar` появляются только в режиме `release/acquire`. они устанавливают отношение happens-before между записью данных и их чтением, поэтому в этом режиме аномалий ноль на всех платформах.

## QEMU

результат — 0 аномалий даже на `relaxed`, хотя бинарник честно собран под aarch64. это ограничение пользовательского режима QEMU: он транслирует обычные load/store гостя в обычные load/store хоста-x86, который работает в модели TSO, и сам слабую модель памяти не моделирует. поэтому StoreStore/LoadLoad-перестановки под `qemu-user` не возникают.

вывод: QEMU годится, чтобы проверить, что программа собирается и запускается под ARM. но reordering на нем не продемонстрировать.

## сравнение трех режимов флага

* `bool`/`volatile int`

   это гонка данных и, формально, UB. кроме аппаратного, добавляется компиляторное переупорядочивание: при оптимизации компилятор вправе закэшировать флаг в регистре.

* `std::atomic<int>` + `relaxed`

   снимает компиляторные проблемы: гарантирует атомарность самой переменной, отсутствие рваных чтений, запрет на выкидывание загрузки из цикла. но `relaxed` не устанавливает порядок между разными переменными — `data` и `ready` остаются независимыми. поэтому на слабой модели ARM аномалии сохраняются. на x86 — 0, так как там порядок обеспечивает TSO.

* `release` + `acquire`

   правильное решение. создает happens-before: все, что записано до `release`-store, видно после соответствующего `acquire`-load. аномалий 0 на любой архитектуре.

## выводы

1. переупорядочивание доступа к памяти реально и наблюдаемо.
2. разница объясняется моделями памяти: x86 — сильная (TSO, запрещает StoreStore/LoadLoad), ARM — слабая (разрешает).
3. `relaxed`-атомики не спасают от этого класса ошибок: они гарантируют атомарность отдельной переменной, но не порядок между переменными. корректность дает только `release`/`acquire` или более сильные модели.
4. `qemu-user` для демонстрации reordering непригоден — он не моделирует слабую память.
