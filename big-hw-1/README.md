# ДЗ: Клиентская нода подбора паролей

Консольное приложение на C++: подключается по TCP к управляющему серверу, получает диапазон кандидатов и целевой хэш, параллельно перебирает ключи и отправляет результат.

## Сборка и запуск

```bash
make
./app <host> <port> <путь_к_файлу_hashrate>
```

В файле hashrate — одно целое число: оценка числа вычислений `sha1(md5(key))` в секунду (для сервера).

## Проверка

`test_server.py` — простой сервер на Python с той же схемой хэша, что и клиент:

```bash
python3 test_server.py 12345
./app 127.0.0.1 12345 hashrate.txt
```

## Протокол взаимодействия клиента и сервера

### Транспорт и кодирование

| Параметр            | Значение                                                       |
|---------------------|----------------------------------------------------------------|
| Транспорт           | TCP/IP, IPv4 (`AF_INET`, `SOCK_STREAM`)                         |
| Инициатор           | Клиент (активное подключение к `host:port`)                     |
| Кодировка           | ASCII, текст                                                    |
| Кадрирование        | построчное: одно сообщение = одна строка                       |
| Разделитель строк   | `\n` (LF). Допускается `\r\n` — символ `\r` при приеме игнорируется |
| Разделитель полей   | пробел (` `)                                                    |
| Регистр команд      | значимый (`TASK`, `WAIT`, `DONE`, `HASHRATE`, `FOUND` и т.д.)   |

Каждое сообщение завершается символом `\n`. Пустые строки трактуются как ошибочные.

### Общий формат сообщения

```sh
<КОМАНДА> [<арг1> [<арг2> ...]]\n
```

Первое слово строки — команда, последующие слова, разделенные пробелами, — аргументы. Набор и число аргументов зависят от команды.

После начального рукопожатия протокол работает по схеме «запрос–ответ»: на каждое сообщение клиента сервер отвечает ровно одной командой, на которую клиент в свою очередь отвечает.

### Сообщения клиента → сервер

| Сообщение            | Назначение                                                   |
|----------------------|--------------------------------------------------------------|
| `HASHRATE <N>`       | Регистрация / объявление производительности                  |
| `FOUND <key>`        | Ключ найден в выданном диапазоне                             |
| `NOT_FOUND`          | Ключ в выданном диапазоне отсутствует                        |
| `ERROR <reason>`     | Полученное от сервера сообщение некорректно                  |

- `HASHRATE <N>` — `N` целое положительное число, оценка количества вычислений `sha1(md5(key))` в секунду. Отправляется сразу после установления соединения и повторно — после команды `WAIT`.
- `NOT_FOUND` — без аргументов.

### Сообщения сервер → клиент

| Сообщение                              | Назначение                              |
|----------------------------------------|-----------------------------------------|
| `TASK <hash> <range_start> <range_end>`| Выдать диапазон на перебор              |
| `WAIT <seconds>`                       | Ожидать `seconds` секунд, затем повтор  |
| `DONE`                                 | Завершить работу                        |

- `TASK` — три аргумента:
  - `hash` — целевой хэш, 40 hex-символов.
  - `range_start`, `range_end` — границы диапазона ключей.
- `WAIT <seconds>` — целое число секунд. Если значение <= 0, клиент использует 1 секунду. По истечении паузы клиент повторно отправляет `HASHRATE`.
- `DONE` — без аргументов, клиент закрывает соединение и завершает работу.

### Спецификация полей

#### `key`, границы диапазона

- Длина: от 1 до 32 символов.
- Допустимые символы: `[0-9A-Za-z]`.
- Любой символ вне этого набора делает значение некорректным.

#### `hash`

- Ровно 40 hex-символов (выход SHA-1).
- При приеме регистр не важен: клиент нормализует хэш к нижнему регистру перед сравнением. Внутреннее вычисление дает хэш в нижнем регистре.
- Схема хэширования: `sha1(md5(key))`, где `md5(key)` берется в виде 16 «сырых» байт, а SHA-1 считается именно от этих 16 байт.

#### `shortlex` – порядок ключей и диапазон

Перебор и сравнение границ используют порядок shortlex (длина важнее содержимого):

1. более короткая строка всегда меньше более длинной.
2. при равной длине строки сравниваются посимвольно по индексу символа в алфавите `0-9A-Za-z` (то есть `'0' < '9' < 'A' < 'Z' < 'a' < 'z'`).

Диапазон `[range_start; range_end]` включает обе границы. Клиент проверяет условие `range_start <= range_end`, при нарушении — `ERROR invalid_range`.

#### `HASHRATE`

Целое положительное число — оценка `sha1(md5(key))`/сек. Берется клиентом из файла, путь к которому передан в командной строке. Сервер может использовать это значение для балансировки размеров выдаваемых диапазонов (на стороне клиента значение только сообщается).

### Обработка ошибок

При получении некорректного сообщения клиент отвечает `ERROR <reason>` и продолжает работу (соединение не разрывается), ожидая следующую команду.

| Ответ клиента             | Причина                                                  |
|---------------------------|----------------------------------------------------------|
| `ERROR malformed_task`    | в `TASK` отсутствует один из трех аргументов             |
| `ERROR invalid_hash`      | поле `hash` не является 40 hex-символами                 |
| `ERROR invalid_range`     | недопустимые символы в границах **или** `start > end`    |
| `ERROR empty_message`     | получена пустая строка                                   |
| `ERROR unknown_command`   | неизвестная команда                                      |

Сетевые ошибки (обрыв соединения, ошибки `recv`/`send`) приводят к корректному завершению клиента с диагностикой в `stderr`. Аварийного завершения при штатных ошибках не происходит.

### Завершение работы и сигналы

Клиент перехватывает `SIGINT`, `SIGTERM`, `SIGHUP`. По сигналу:

1. выставляется флаг завершения.
2. на сокете вызывается `shutdown(SHUT_RDWR)`, чтобы разблокировать `recv`.
3. рабочие потоки перебора корректно останавливаются (проверяют флаг).
4. сокет закрывается, ресурсы освобождаются.

Незавершенная задача при этом результат не отправляет.
